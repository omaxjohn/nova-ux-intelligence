# Verify operations

HARDEN addresses boundaries and failure recovery; OPTIMIZE improves measured bottlenecks without degrading downstream outcomes; EXTRACT turns validated local patterns into reusable guidance with applicability limits.

For runtime signoff, provide a compact action sequence: render the identified release build → compare it with the approved design or specified expected behavior under matching task/content/viewport/theme/locale → inspect critical interactions → fix failures → render again and repeat affected checks. Name the comparison target in the response; if unavailable, record that limitation. Inspect font fallback, line-height, image crop, glass contrast, overflow, sticky occlusion, RTL and focus as applicable. A build, source declaration, HTTP success or approved design cannot substitute for these results.

Keep a verification record with required slots: check/task, environment and artifact identity, expected behavior, observed behavior, status (executed/passed, failed, planned, blocked), evidence and remaining limitation. No browser means runtime verification is blocked; source review can still proceed. Do not block unrelated low-impact advice on an unavailable browser.

For critical flows, apply Typical / Empty / Minimum / Maximum / Invalid / Loading / Failed / Offline / Localized / Accessibility-adjusted states. Cover:

- Missing images, prices and reviews; honest unavailable states, no fabricated values.
- Long and mixed-direction text, narrow/wide viewports, zoom/font scaling and content extremes.
- Slow/offline/timeout, sold out, session expiry, retry, preserved non-sensitive progress, duplicate actions and reconciled transaction status.
- Keyboard/focus, semantics, accessible names/roles/values, screen-reader behavior, labels/error association, contrast, reduced motion and relevant input modes.
- Component/token integrity, loaded assets, device performance and visual craft.

Select cases from the actual risks, not every permutation for every component. Keep critical failures in the release decision; do not report a checklist as completed work.

Verification asks whether specified behavior works. Validation asks whether users can achieve the intended outcome. For validation, choose realistic tasks and appropriate user evidence; measure informed completion and downstream consequences. A single AI example is not user validation. Record measured conditions before making performance or conversion claims.

For EXTRACT, retain context, evidence, counterexamples, limitations and last verification date. An attractive pattern without task validation remains a candidate, not a validated reusable rule. Refresh dynamic knowledge without changing frozen reasoning semantics.
